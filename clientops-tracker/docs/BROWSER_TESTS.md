# Browser Verification

`pnpm test` runs Vitest API/database tests. It does **not** run the browser suite.
Run `pnpm test:e2e` separately. There are four Playwright scenarios in
`e2e/portal.spec.ts`, with axe WCAG 2 A/AA and 2.1 AA assertions on the checked pages.

## Environment and Exact Command

Requirements: Node.js 24, pnpm 9.15.4, Docker Desktop with Linux containers (or
Docker Engine and Compose on Linux), port 8180 available, and installed Chrome.
Use a fresh disposable verification database, never a personal or production database.
The test runner starts its own clean browser profile, not your personal profile.

From a fresh checkout in PowerShell:

```powershell
cd "C:\Users\PnP\Desktop\Client Tracker\clientops-tracker"
pnpm.cmd install --frozen-lockfile
# Remove inherited overrides from this shell; Compose must use the verification example.
Remove-Item Env:DATABASE_URL,Env:JWT_SECRET,Env:TEST_DATABASE_URL,Env:DISPOSABLE_DATABASE_NAME -ErrorAction SilentlyContinue
function dc { docker compose -p clientops-readiness --env-file .env.verify.example -f docker-compose.prod.yml @args }
dc build
dc up -d --wait postgres
dc run --rm --no-deps api node dist/migrate.js
# Destructive ONLY to the explicitly designated clientops_verify_demo database:
dc run --rm --no-deps -e NODE_ENV=development -e DISPOSABLE_DATABASE_NAME=clientops_verify_demo -e SEED_RESET=true api node dist/seed.js
dc up -d --no-build --wait
dc up -d --no-deps --force-recreate --wait nginx
$env:VERIFY_URL='http://localhost:8180'
$env:E2E_ALLOW_DISPOSABLE_DEMO='true'
$env:BROWSER_CHANNEL='chrome'
pnpm.cmd test:e2e
```

On a TLS-inspected machine use the optional trusted-CA build override in
[DEPLOYMENT.md](DEPLOYMENT.md), never disable TLS validation. If Chrome is not
installed, run `pnpm exec playwright install chromium` and unset `BROWSER_CHANNEL`.
Linux CI installs Chromium with `pnpm exec playwright install --with-deps chromium`.
The config refuses non-loopback URLs or a missing explicit disposable-demo opt-in.
Reseed only the verification database before repeating the complete suite: the
first scenario creates one fictional ticket and comments.

## Four Scenarios

1. **Administrator, developer and client workflow:** failed login; real tables,
   filters and empty state; create ticket; saved pending triage after refresh;
   apply once; internal/public comments and client privacy; header at multiple
   scroll positions; dropdown saving/saved feedback, persistent status/priority/
   category; injected HTTP 503 error with the previous value retained; mobile
   badges and keyboard horizontal scrolling. Successful mutations use the real
   Express API and PostgreSQL. Only the error-path request is intercepted.
2. **Swagger:** documentation renders through the Nginx origin.
3. **Mobile keyboard navigation:** focus enters and stays in the drawer; Escape
   closes it and restores focus to the opener.
4. **Sessions:** invalid JWT clears storage and redirects; logout reaches another tab.

## Reports and Screenshots

- HTML report: `playwright-report/index.html`. Open with
  `pnpm exec playwright show-report playwright-report` (default localhost:9323).
- Machine-readable results: `test-results/browser-results.json`.
- Failure attachments: `test-results/`; scroll-position screenshots also appear
  as attachments in the HTML report.
- Public fictional screenshots: `docs/assets/screenshots/`, listed in
  [SCREENSHOTS.md](SCREENSHOTS.md). Full-page captures reset scroll to zero first.
- Report metadata records Git HEAD, whether the working tree was dirty, browser
  choice and target URL. Local screenshots generated by the suite can dirty Git;
  metadata describes the state when the run started, not a release certification.
- CI uploads reports and screenshots as `browser-evidence-<full-head-sha>` even
  when a scenario fails. Download from the linked Actions run; unzip and open the
  HTML report. Generated reports stay ignored in Git.
  CI sets `E2E_SCREENSHOT_DIR=test-results/screenshots` so artifacts contain only
  that run's captures, never old screenshots from the repository.

See [RELEASE_READINESS.md](RELEASE_READINESS.md) for revisions actually tested and
hosted run links. No report here implies publication or public deployment. Axe
checks are focused automated coverage, not an accessibility certification.
